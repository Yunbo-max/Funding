# /search — Worldwide research funding discovery, grounded in official calls

Read `skills/funding-autopilot/commands/02-discover.md`, `references/discovery.md`, and `assets/source-registry.json`. The user may target **any countries or regions**; never assume that a UK PhD, a current institution or the bundled UKRI adapter restricts their search to the UK.

**Scope truth:** This is a global **agent-driven search workflow**, not an exhaustive built-in global funding database. The standalone Python UKRI RSS connector covers only a recent feed; other funders need the host's real web/search tools or explicitly developed adapters. An inaccessible funder is a coverage gap, not evidence that no funding exists there.

## Steps

1. Load the **user-reviewed, uploaded-CV-based** profile and their requested regions, host mobility, salary needs and independent/new-PI routes. If the user says "worldwide", cover multiple relevant geographic lanes rather than quietly limiting to the current country. Do not infer residence, nationality, immigration/work rights or PI consent.
2. Generate region-specific search plans (per geography): exact research field and synonyms, interdisciplinary applications, eligible applicant career stage, independent fellowships, **new PI/host-funded** awards, research-prize/industry grants when appropriate. Evaluate grants paying the researcher separately from project funds held by a PI.
3. Consult **official national/regional funders**, programme websites and receiving institutions. Examples of discoverable portal lanes are UKRI and UK foundations; EU/Horizon/DFG; US NSF/NIH; Canadian NSERC; Australian ARC; Japan JSPS; Singapore NRF; Brazil FAPESP; South African NRF; New Zealand Royal Society. These URLs are starter portals in `source-registry.json`, **not validated live calls**. Search beyond the registry as needed. Use language-aware terms where useful.
4. Use the permitted UKRI RSS through `workspace.py search` **only when a UK lane is relevant**; no UKRI-only fetch should be described as a worldwide search. For all other lanes, use the host's *actual current web/browser/search tools*, collect official-link leads to private `discovered-calls.json`, and import using `workspace.py search --input-file private/discovered-calls.json`. Do not claim a live scrape if you only browsed an index page.
5. For a bounded set of promising leads, read the **specific current-round** official call and all relevant accessible PDF/FAQ guidance. Verify applicant/PI/host career requirements, timing of doctorate milestones, eligibility of salary and costs, official funder deadline plus *receiving institution's internal deadline*, required sections/limits and award location/citizenship restrictions. If the user seeks another country, check whether the award is **open to international applicants and whether a local eligible host is compulsory**. Preserve exact source URL, section locator and checked-at UTC.
6. Record exact programme/round identity in the private ledger. Promote unverified leads using `workspace.py verify --key <lead> --call-file private/verified-call.json`. Duplicate search sightings preserve history; new rounds are different opportunities. 403, dead link, stale PDF, ambiguous date and missing host confirmation remain explicit `unverified/conditional`, not `eligible`.
7. Show source-linked leads grouped by **verified, conditional, ineligible, expired, and unverified**; list searched regions/source lanes and important gaps to avoid false completeness. Recommend `/match` next (or legacy `/rank`), which applies the true eligibility gates before opportunity ranking.

Never send a CV, correspondence or proposal to a funding site during discovery. Save researcher-specific artifacts only in ignored `private/`.
